# GTNH Server Updater

Electron application for preparing a new GTNH server directory on a remote Linux host over SSH.

The first implemented slice provides:

- SSH private-key authentication, saved profiles first: picking a profile loads its paths and tests the server at once, connection details stay collapsed until edited;
- remote directory browsing and absolute path entry (every path the user provides is trimmed before it is used), with the newest GTNH version and daily build published on GitHub shown under the destination, so the new folder can carry the version name;
- local ZIP upload over SFTP or server-side HTTPS download;
- strict path, archive, tool, permission and disk-space preflight;
- destructive destination confirmation by exact resolved path;
- direct extraction, followed by matching owner, group and Unix permissions to the old server; existing paths retain their access, new paths inherit the nearest old directory (regular files retain executable bits only when permitted there);
- partial files preserved and reported after extraction or permission failures, including when the SSH account cannot set the required ownership.

The second slice carries over user changes with a three-way comparison:

- the new server folder is created when it is missing (deployment skipped, path typed by hand), and comparing against an empty new server is refused by name instead of failing on a raw shell error;
- the original archive of the old version is required and extracted temporarily next to the new server; it and the new archive can be a local ZIP, an HTTPS URL, or a build picked from the GTNH daily releases;
- files are compared by `sha256sum` across old server, original archive and new server, with fixed and user glob exclusions;
- only files changed or added by the user are proposed; everything else follows the new version;
- known configuration formats (Forge .cfg, .properties, .ini, .json) are compared key by key, so files a mod rewrote at startup (reworded comments, options added with their default value, reordering) are not proposed and appear under a "Regenerated by mods" filter;
- conflicting text files open in Monaco, the VS Code editor: the original archive, your version and the new version side by side, then the pre-merged result to edit, with Git-style conflict markers that must be resolved before writing; binary, non UTF-8 and >2 MiB files are chosen whole;
- any reviewed text file can use an edited result, including files changed only by you; output retains the new file's text format, or the old file's format when the new file is absent;
- files only in the old server are proposed (and ticked) under `serverutilities/` and `journeymap/`; elsewhere mods recreate them, so they stay behind the "Created by mods" filter;
- changes are applied in one batch to the new server only, with atomic replacement that preserves owner, group and Unix permissions.

The third slice migrates the world once the user confirms the old server is stopped:

- the world is the old `level-name` folder; the new `server.properties` level-name is aligned to it;
- server-side world data outside the world folder comes from ServerUtilities `additional_backup_files` (GTNH default list as fallback) and is excluded from the merge;
- each path is copied with `cp -a` to a temporary name, verified by file count and bytes, then renamed;
- existing targets require the exact world path to be typed; failures keep partial files and report them.

The fourth slice hardens connections:

- host keys are checked against `~/.ssh/known_hosts` and an app-owned known_hosts; unknown hosts need an explicit fingerprint trust, changed keys are refused;
- named SSH profiles are stored in the app data folder; a passphrase is stored only when the OS can encrypt it (Electron `safeStorage`, never the Linux `basic_text` fallback);
- every remote step can be cancelled; long commands run in their own process group, killed when the SSH channel closes; app temporaries are removed after a failure or cancellation, partial destination files are kept and reported;
- a single app instance runs one operation at a time, closing during an operation asks for confirmation, and a secret-free log is written to the app data `logs` folder.

The fifth slice completes the user journey and delivery:

- a guided stepper (Server, Stop old server, Deploy, Carry over changes, Migrate world, Report) where merge and migration can be skipped explicitly, and the report can be saved as Markdown;
- a typed IPC contract (`src/shared/ipc.contract.ts`): the preload forwards only listed channels, and the main process accepts calls from the main window only and validates every payload with zod;
- NSIS, AppImage and deb packages with Electron fuses and GitHub-based auto-update.

A second mode, **Mods**, replaces one mod with your own build (header tab, same SSH profile):

- choose the folder your builds land in (e.g. `build/libs`); each JAR's single mcmod.info modid identifies the mod, one entry per version is proposed (its newest build; `-dev`, `-sources` and similar JARs are ignored), and the folder is remembered per modid;
- targets: the server of the profile, found from its systemd unit (`gtnh` by default, saved with the profile; the unit's `WorkingDirectory` is the server folder, root account required), and the Prism instances you tick (default `%APPDATA%\PrismLauncher\instances` or `InstanceDir`, overridable); the original is the only JAR of `mods/` or `mods/1.7.10/` declaring the modid, and running instances are refused;
- the server goes first: upload, `systemctl stop`, original moved to `mods-backup/<modid>/<date>/`, new JAR under its own name with the original's owner and mode, `systemctl start`, then `logs/fml-server-latest.log` is watched for `FMLServerStartedEvent`; a crash report, an unexpected exception, a relaunch by the start script, a dead service or 10 minutes stop the service and report the log; Prism instances change only after a successful start;
- "Restore original" puts back the original of the current backup chain, with the same restart and check; five backups are kept per modid (the original and the four latest);
- the update journey excludes `/mods-backup/` and its report lists custom mods still active in the old server, since they are not carried over.

All design decisions are recorded in the [Wayfinder map](.scratch/gtnh-server-updater/map.md); the [validation matrix](.scratch/gtnh-server-updater/spec.md#matrice-de-validation) maps each requirement to its tests.

## Development

Requirements: Node.js 26+, pnpm 12, and a Linux target with a POSIX shell, `curl`, `unzip`, `find` and GNU coreutils and findutils (`sha256sum`, `stat`, `chown --reference`, `chmod --reference`, `cp -a`, `find -printf`) and `setsid` (util-linux).

```bash
pnpm install
pnpm dev
```

Validation commands:

```bash
pnpm check      # vp check: Oxfmt + Oxlint (type-aware, type checking)
pnpm test run   # vp test (Vitest via Vite+)
pnpm build      # electron-vite build
pnpm smoke:ui
pnpm icons      # build/icon.png and build/icon.ico from src/renderer/public/icon.svg
```

The app does not use `sudo` and never writes to the old server path. Interrupted steps are not resumed: run the step again, its checks are redone.

### End-to-end tests

`pnpm test:e2e` runs deployment, merge, migration, cancellation and orphan handling against a real Linux host. It is skipped unless `GTNH_E2E_HOST` is set; the host key must already be in `~/.ssh/known_hosts`. Work happens in a fresh `/root/gtnh-e2e/run-<uuid>` directory (override with `GTNH_E2E_ROOT`) that is removed afterwards.

```bash
python scripts/make-e2e-fixtures.py /tmp/gtnh-fixtures
GTNH_E2E_HOST=ely-minecraft GTNH_E2E_FIXTURES=/tmp/gtnh-fixtures pnpm test:e2e
```

The test host is now the production server `ely-minecraft`: every e2e run works in its own directory and leaves the live server untouched. `src/main/e2e/mods.e2e.test.ts` exercises the Mods mode on the same host with a throwaway runtime unit `gtnh-mods-e2e-<id>` in `/run/systemd/system` and a fake server under `GTNH_E2E_ROOT` (replace, failed start, restore), both removed afterwards; `GTNH_E2E_REAL_SERVICE` also inspects a real unit, read only.

Optional variables: `GTNH_E2E_USER` (root), `GTNH_E2E_KEY` (`~/.ssh/id_ed25519`), `GTNH_E2E_PORT`. Set `GTNH_E2E_REAL_OLD` (a real installation on the host) with `GTNH_E2E_REAL_BASE` (its local original archive) and optionally `GTNH_E2E_REAL_NEW` to also exercise a real GTNH installation; the base archive is also used to test cancelling an upload.

`pnpm smoke:ipc` starts the real main process and calls the IPC bridge against `GTNH_E2E_HOST`.

### Packaging and releases

`pnpm dist:docker` builds the Windows NSIS installer and the Linux AppImage and deb in one Docker container (`electronuserland/builder:wine`, see `docker/Dockerfile`) into `dist/`, from Windows or Linux, without publishing; `pnpm release:docker` does the same and publishes (needs `GH_TOKEN`). Dependencies are installed inside the container; pnpm, Electron and electron-builder caches are kept in the `gtnh-updater-*` Docker volumes. `pnpm dist:win` and `pnpm dist:linux` build natively for the current platform only. `pnpm release:win` / `pnpm release:linux` publish to the GitHub releases of `Elyspio/gtnh-server-updater` and need `GH_TOKEN`; the installed app checks those releases at startup, downloads updates in the background and installs them on restart or quit, never during a remote operation.
